# Прогресс

## Сейчас

Шаг 1 завершён. Следующий — **шаг 2: `Request` / `Response`**.

Суть шага 2: обработчик становится функцией `Response handle(Request)` — возвращает значение,
а не пишет в поток. `Request` и `Response` — records. Правила записи ответа (порядок, длина
в байтах, закрытие) живут в одном адаптере `Response` → `HttpExchange`, и обработчик нарушить
их не может. Из Java: records, компактные конструкторы, статические фабричные методы.
Ближайший аналог в Spring — `ResponseEntity`. Полную постановку задачи Claude даёт в начале шага.

## Сделано

### Шаг 1. `Main` — голый HttpServer

2026-09-18, коммит `58e3b1c`. `HttpServer` на порту 8080, executor на виртуальных потоках,
один контекст на `/`. `GET /health` → 200 и `{"status":"ok"}`, всё остальное → 404.
Shutdown hook со `stop(2)`.

Выводы, каждый проверен экспериментом:

- Без `setExecutor` обработчик выполняется прямо в потоке `HTTP-Dispatcher`, который
  принимает соединения. Запросы идут строго по очереди: два запроса по 2 с занимают 4 с.
- 10 000 задач по 200 мс ожидания: пул из 200 платформенных потоков — 10,2 с, виртуальный
  поток на задачу — 0,24 с. Виртуальные потоки удешевляют ожидание, а не вычисления.
- Контекст `HttpServer` совпадает по префиксу строки: контекст `/health` отвечал и на
  `/healthcheck`. На незарегистрированные пути JDK отвечает своей HTML-страницей 404.
  Поэтому контекст один — `/`, а разбор путей наш.
- Порядок ответа: заголовки → `sendResponseHeaders` → тело → `close`. Заголовок,
  выставленный после `sendResponseHeaders`, молча пропадает.
- Второй аргумент `sendResponseHeaders`: `n` — длина тела в байтах, `-1` — тела нет,
  `0` — chunked. Длина в символах вместо байтов («привет»: 6 против 12) даёт
  `too many bytes to write to stream`, а клиент получает пустой ответ.
- Необработанное исключение в обработчике: клиенту — `Empty reply from server`,
  в логах — ничего.
- Обработчик, который не отправил ответ и не закрыл `exchange`, вешает клиента навсегда.
- Без `start()` нет потока `HTTP-Dispatcher` — единственного не-демона. `main` заканчивается,
  и процесс выходит.
- Shutdown hook срабатывает от SIGINT (`Control+C`, код выхода 130) и SIGTERM (`kill`,
  `docker stop`, код 143), но не от SIGKILL (`kill -9`). Код выхода = 128 + номер сигнала.
- `stop(n)` сразу закрывает порт и ждёт текущие запросы не дольше `n` секунд: `stop(5)`
  дождался 3-секундного запроса за 2,6 с, `stop(1)` оборвал его.
- `Control+C` не работает в окне Run в IDEA: у процесса нет терминала (`tty=??`).
  Останавливать кнопкой Stop или `kill`.
- `import module jdk.httpserver` не подтягивает `java.base` — нужен второй импорт.
  Импорт модулей может дать неоднозначность имён: `Authenticator` есть в обоих модулях,
  лечится точечным импортом.
- `maven.compiler.release` лучше пары `source`/`target`: проверяет ещё и API целевой версии.
  Без него плагин компилятора собирает как Java 8.
